# Week 1 Journal — Ticket Resolution

## Ticket 1: Gateway routes returning 404

### Command

curl.exe http://localhost:8080/test/get

### Error:

404 Not Found — request never reached the configured route, no matching
mapping found by the gateway.

### Relevant Context

In `application.properties`, routes were originally configured as:

    spring.cloud.gateway.routes[0].id=test-route
    spring.cloud.gateway.routes[0].uri=https://httpbin.org
    spring.cloud.gateway.routes[0].predicates[0]=Path=/test/**
    spring.cloud.gateway.routes[0].filters[0]=RewritePath=/test/(?<segment>.*), /${segment}

Dependency in use: `spring-cloud-starter-gateway-server-webmvc`
(Spring Cloud version `2025.1.2`)

### Key Observation

`spring.cloud.gateway.routes[...]` is the property prefix for the classic
**reactive** (Netty) gateway. This project uses the newer **MVC-flavoured**
gateway (`gateway-server-webmvc`), which as of Spring Cloud 2025.0.0 requires
a different prefix: `spring.cloud.gateway.server.webmvc.routes[...]`. The
older `spring.cloud.gateway.mvc.routes[...]` prefix also exists but is
deprecated. Tomcat starting (instead of Netty) was correct behaviour for
this dependency, not a bug — it was a red herring during initial debugging.

### Resolution

Updated all route properties to use the `spring.cloud.gateway.server.webmvc.routes[...]`
prefix. Restarted the app fully (not relying on DevTools auto-restart, since
config changes need a clean reload). Verified via `curl.exe` that `/test/get`
now correctly proxies to `httpbin.org` and relays the response.

## Ticket 2: PowerShell curl throwing script-execution warning

### Command

curl http://localhost:8080/test/get

### Error:

    Security Warning: Script Execution Risk
    Invoke-WebRequest parses the content of the web page. Script code in
    the web page might be run when the page is parsed.
    [Y] Yes  [A] Yes to All  [N] No  [L] No to All  [S] Suspend  [?] Help

### Relevant Context

Running on Windows PowerShell. `curl` is aliased by PowerShell to
`Invoke-WebRequest`, which is not the same binary as real curl and applies
its own content-parsing safety checks on responses.

### Key Observation

The warning is unrelated to the gateway itself — it's PowerShell being
cautious about parsing plain-text/HTML in the response body, not a real
error. It surfaced because our 429 rejection response is plain text, which
`Invoke-WebRequest` treats differently from JSON.

### Resolution

Used `curl.exe` explicitly instead of the bare `curl` alias, which invokes
the real curl binary and bypasses PowerShell's `Invoke-WebRequest` wrapper
entirely. Confirmed this resolves the warning permanently for all future
requests.
