# Week 1 Journal — Gateway & Rate-Limiting Core

**Workstream:** Gateway and rate-limiting logic

## Objective

Build the smallest useful version of the API Gateway: a reverse proxy that forwards requests to a target API and returns HTTP 429 once a per-client request budget is exhausted — no persistence, no dashboard, single naive algorithm.

## Setup

- Generated project via Spring Initializr: Spring Boot (parent 4.1.0), Java 17, Maven
- Dependencies: `spring-cloud-starter-gateway-server-webmvc`, `spring-boot-devtools`, `lombok`, `spring-boot-starter-test`
- Spring Cloud version: `2025.1.2`

## Work Completed

1. **Reverse proxy route** — configured a route in `application.properties` forwarding `/test/**` to `https://httpbin.org`, with `RewritePath` stripping the `/test` prefix before forwarding.
2. **Verified end-to-end forwarding** — confirmed via `curl.exe http://localhost:8080/test/get` that the gateway correctly proxies to httpbin and relays the JSON response back unmodified.
3. **Naive rate limiter** — implemented `RateLimitFilter` (a `HttpFilter` bean) using an in-memory `AtomicInteger` counter. First 5 requests to `/test/**` are forwarded; the 6th onward is rejected with `429 Too Many Requests` and a `Retry-After` header, without reaching the origin.
4. **Verified rejection behaviour** — fired 6+ sequential requests via curl and confirmed requests 1–5 return httpbin's JSON and request 6+ returns the rate-limit rejection message.

## Issues Faced and Resolved

- **404 on all routes initially.** Root cause: `spring-cloud-starter-gateway-server-webmvc` (the newer MVC-flavoured gateway) uses the property prefix `spring.cloud.gateway.server.webmvc.routes[...]`, not the classic `spring.cloud.gateway.routes[...]` used in most tutorials (which apply to the reactive/Netty gateway) or the deprecated `spring.cloud.gateway.mvc.routes[...]` (older MVC gateway, deprecated as of Spring Cloud 2025.0.0). Fixed by updating the property prefix; confirmed Tomcat starting was correct behaviour for this dependency, not a bug.
- **PowerShell's `curl` alias** (actually `Invoke-WebRequest`) threw parsing errors and script-execution warnings on plain-text responses. Resolved by using `curl.exe` explicitly to invoke real curl.

## Known Limitations (by design, to be addressed Week 2)

- **Counter is global, not per-client** — all callers currently share the same 5-request budget.
- **Counter never refills** — once exhausted, the gateway stays locked until restart (a quota, not a rate limit).
- **No distributed correctness** — this won't hold up with multiple gateway instances, which is the actual engineering problem the project is meant to solve.

## Next Steps (Week 2)
