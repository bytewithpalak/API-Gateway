# Week 1 Journal — Persistence, Auth & Backend Plumbing

**Workstream:** Persistence, Auth & Backend Plumbing

## Objective

Stand up the multi-tenant backbone the gateway and dashboard both depend on: JWT-based signup/login, an API registration endpoint that stores a target URL + budget + algorithm choice, and the Postgres schema underneath it — no rate-limiting logic, no frontend, just accountable storage and auth.

## Setup

- Generated project via Spring Initializr: Spring Boot 3.3.2, Java 17, Maven
- Dependencies: `spring-boot-starter-web`, `spring-boot-starter-data-jpa`, `postgresql`, `spring-boot-starter-security`, `spring-boot-starter-validation`, `jjwt-api`/`jjwt-impl`/`jjwt-jackson` (0.12.5), `spring-boot-starter-test`
- Local Postgres instance, schema applied manually from `schema.sql` (kept `ddl-auto=validate` deliberately, not `update`, so schema drift shows up as a startup failure rather than a silent auto-migration)

## Work Completed

1. **Entity/schema design** — four tables: `users`, `registered_apis`, `policies`, `request_logs`, matching the proposal's data model. `policies` is a separate table from `registered_apis` (1:1) rather than inlined, so the algorithm/budget can be swapped without touching ownership data.
2. **JWT auth** — `JwtUtil` (HS256, secret loaded from `JWT_SECRET` env var, rejects anything under 32 bytes at startup) and `JwtAuthFilter` (`OncePerRequestFilter`, reads `Authorization: Bearer <token>`, populates `SecurityContext`). Wired into `SecurityConfig` as stateless, `/api/auth/**` and `/actuator/health` public, everything else requires a valid token.
3. **Signup/login** — `AuthController` + `AuthService`, passwords hashed with BCrypt, never stored or logged in plaintext. Verified via `curl.exe`: signup returns a token, that token is accepted on a protected route, a missing/expired token returns 401.
4. **API registration** — `ApiRegistrationController`/`ApiRegistrationService`. Authenticated user submits name + target URL + algorithm + budget; a `RegisteredApi` row and its paired `Policy` row are written in one transaction; a gateway API key (UUID) is generated for the caller.
5. **URL validation (proxy-abuse mitigation)** — `UrlValidationService` resolves the target host and rejects loopback, link-local, site-local (RFC1918), any-local, multicast, and the `169.254.169.254` metadata address before anything is persisted. Verified: `http://localhost:8080` and `http://169.254.169.254/...` are both rejected with a 400; a real public URL is accepted.

## Issues Faced and Resolved

- Initial `PasswordEncoder` bean collision — had briefly declared it in two config classes while restructuring; consolidated into `SecurityConfig` only.
- `InetAddress.getByName()` for the SSRF check does a live DNS resolution, which meant validation could throw on a genuinely offline network during testing rather than cleanly rejecting — noted, not yet handled distinctly from "malformed/unregistrable" (see limitations).
- Jackson couldn't serialize `Instant` fields by default in earlier testing; resolved by relying on Spring Boot's auto-registered `jackson-datatype-jsr310` rather than a manual converter.

## Known Limitations (by design, to be addressed Week 2)

- No rate-limit enforcement lives here yet — `registered_apis`/`policies` are pure storage; Person 1's gateway hasn't been pointed at them yet, so a registered API isn't actually protected end-to-end.
- Request logging (`RequestLogService.logAsync`) exists and is `@Async`, but nothing calls it yet since the proxy path isn't wired to this service — no real request has been logged.
- DNS-failure vs. genuinely-invalid-host aren't distinguished in `UrlValidationService` — both currently surface as the same 400.
- No integration tests yet against a real Postgres instance (currently manual `curl` verification only).
