# Week 1 Journal — Persistence, Auth & Backend Plumbing

**Workstream:** Persistence, Auth & Backend Plumbing

## Objective

Stand up the multi-tenant backbone the gateway and dashboard both depend on: JWT-based signup/login, an API registration endpoint that stores a target URL + budget + algorithm choice, and the Postgres schema underneath it — no rate-limiting logic, no frontend, just accountable storage and auth.

## Setup

- Generated project via Spring Initializr: Spring Boot 3.3.2, Java 17, Maven
- Dependencies: `spring-boot-starter-web`, `spring-boot-starter-data-jpa`, `postgresql`, `spring-boot-starter-security`, `spring-boot-starter-validation`, `jjwt-api`/`jjwt-impl`/`jjwt-jackson` (0.12.5), `spring-boot-starter-test`
- Local Postgres instance, schema applied manually from `schema.sql` (kept `ddl-auto=validate` deliberately, not `update`, so schema drift shows up as a startup failure rather than a silent auto-migration)

## Work Completed

1. **Entity/schema design** — four tables: `users`, `registered_apis`, `policies`, `request_logs`, matching the proposal's data model. `policies` is a separate table from `registered_apis` (1:1) rather than inlined, so the algorithm/budget can be swapped without touching ownership data.
2. **JWT auth** — `JwtUtil` (HS256, secret loaded from `JWT_SECRET` env var, rejects anything under 32 bytes at startup) and `JwtAuthFilter` (`OncePerRequestFilter`, reads `Authorization: Bearer <token>`, populates `SecurityContext`). Wired into `SecurityConfig` as stateless, `/api/auth/**` and `/actuator/health` public, everything else requires a valid token.
3. **Signup/login** — `AuthController` + `AuthService`, passwords hashed with BCrypt, never stored or logged in plaintext. Verified via `curl.exe`: signup returns a token, that token is accepted on a protected route, a missing/expired token returns 401.
4. **API registration** — `ApiRegistrationController`/`ApiRegistrationService`. Authenticated user submits name + target URL + algorithm + budget; a `RegisteredApi` row and its paired `Policy` row are written in one transaction; a gateway API key (UUID) is generated for the caller.
5. **URL validation (proxy-abuse mitigation)** — `UrlValidationService` resolves the target host and rejects loopback, link-local, site-local (RFC1918), any-local, multicast, and the `169.254.169.254` metadata address before anything is persisted. Verified: `http://localhost:8080` and `http://169.254.169.254/...` are both rejected with a 400; a real public URL is accepted.

## Issues Faced and Resolved

- Initial `PasswordEncoder` bean collision — had briefly declared it in two config classes while restructuring; consolidated into `SecurityConfig` only.
- `InetAddress.getByName()` for the SSRF check does a live DNS resolution, which meant validation could throw on a genuinely offline network during testing rather than cleanly rejecting — noted, not yet handled distinctly from "malformed/unregistrable" (see limitations).
- Jackson couldn't serialize `Instant` fields by default in earlier testing; resolved by relying on Spring Boot's auto-registered `jackson-datatype-jsr310` rather than a manual converter.

## Known Limitations (by design, to be addressed Week 2)

- No rate-limit enforcement lives here yet — `registered_apis`/`policies` are pure storage; Person 1's gateway hasn't been pointed at them yet, so a registered API isn't actually protected end-to-end.
- Request logging (`RequestLogService.logAsync`) exists and is `@Async`, but nothing calls it yet since the proxy path isn't wired to this service — no real request has been logged.
- DNS-failure vs. genuinely-invalid-host aren't distinguished in `UrlValidationService` — both currently surface as the same 400.
- No integration tests yet against a real Postgres instance (currently manual `curl` verification only).

# Week 2 Journal — Persistence, Auth & Backend Plumbing

**Workstream:** Persistence, Auth & Backend Plumbing

## Objective

Close the two concrete gaps left open from Week 1 — no filtering on the dashboard's log endpoint, and no actual instrumentation of the log-completeness metric — and back both with real automated tests instead of manual `curl` verification.

## Setup

- Added Testcontainers to `pom.xml`: `testcontainers-junit-jupiter` and `testcontainers-postgresql` (1.20.1), scoped to `test` only
- Requires Docker running locally (and eventually in CI) since tests now spin up a real, throwaway Postgres container instead of using H2

## Work Completed

1. **Filtering on the logs endpoint** — `GET /api/dashboard/{apiId}/logs` now accepts optional `outcome`, `clientIdentity`, `from`, and `to` params, all combinable, backed by a new `findFiltered(...)` JPQL query in `RequestLogRepository` that treats a `null` filter as "no restriction" rather than requiring separate query methods per combination.
2. **Log-completeness instrumentation** — added `LogCompletenessService` and a `CompletenessResponse` DTO, exposed via `GET /api/dashboard/{apiId}/completeness?expected=...&from=...&to=...`. It compares an externally supplied "expected" request count against actual rows written to `request_logs` in that window and reports the ratio against the proposal's 99.9% target.
3. **Real integration tests, not just manual checks** — `LogCompletenessIntegrationTest` fires 2,000 concurrent calls through the async logger against a real Postgres container and asserts the completeness ratio clears 99.9%; `RequestLogRepositoryFilterTest` verifies the outcome, client-identity, and date-range filters independently, and confirms filtering never leaks rows across `apiId`.
4. **Verified locally** — ran `mvn test` end-to-end with Docker Desktop running; both new test classes pass.

## Issues Faced and Resolved

- A copy-paste import error (`DynamicPropyRegistry` instead of `DynamicPropertyRegistry`) broke compilation on the first pass — caught immediately since it failed the build rather than silently misbehaving.
- First test run was noticeably slower than expected — Testcontainers pulls the `postgres:16-alpine` image from Docker Hub on first use; subsequent runs are fast since the image is cached locally.
- The throwaway test database needed `ddl-auto=create-drop` rather than the app's real `validate` setting, since `schema.sql` isn't applied automatically to a container that only exists for the test's lifetime — kept this scoped to test config only, real deployments still fail loudly on schema drift.

## Known Limitations (carried forward / new this week)

- `LogCompletenessService` can't determine an "expected" count on its own — it depends on a number supplied externally (a load-test tally, or eventually Person 1's gateway keeping its own counter). Not yet wired to a real driver.
- DNS-failure vs. genuinely-invalid-host still aren't distinguished in `UrlValidationService` — not addressed this week, carried over from Week 1.
- No CI pipeline yet — `mvn test` has only been run locally so far, not gated on every push.

# Week 3 Journal — Persistence, Auth & Backend Plumbing

**Workstream:** Persistence, Auth & Backend Plumbing

## Objective

Move from "works locally" to "deployed and integrated" — get CI running the test suite automatically, get the service onto staging, harden login against brute-force attempts, and take the first real integration pass with Person 1's gateway.

## Setup

- GitHub Actions workflow added (`.github/workflows/backend-ci.yml`) running `mvn test` on every push to the backend
- Deployed to Render (Postgres add-on + web service), with `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, and `JWT_SECRET` set as platform-managed environment secrets, never committed

## Work Completed

1. **CI/CD pipeline** — every push now runs the full test suite, including the Testcontainers-based tests, on GitHub-hosted runners (which have Docker available out of the box, so no extra Docker-in-Docker setup was needed). A regression in filtering or log completeness now fails the build instead of reaching staging.
2. **Staging deployment** — backend is live on Render, confirmed `/actuator/health` reachable externally, confirmed signup/login and API registration work against the managed Postgres instance, not just local.
3. **Login hardening** — added a basic per-(IP + email) rate limit on `/api/auth/login` to reduce brute-force risk, since this service already owns all password handling.
4. **`RegisteredApi.active` wired into real checks** — inactive APIs are now treated as unavailable by both the registration listing and (once called) the proxy lookup, laying the groundwork for a degraded-state indicator once Person 1 finalizes the Redis fail-open/fail-closed decision.
5. **First real integration pass with Person 1's gateway** — confirmed `findByGatewayApiKey` resolves correctly when called from the actual gateway code (not just a unit test), and confirmed `RequestLogService.logAsync(...)` gets invoked from a real proxied request for the first time, not just from our own test suite.

## Issues Faced and Resolved

- A mismatch surfaced during integration: the gateway expected the API key in a request header, while our lookup logic had assumed a path variable during earlier standalone testing. Resolved by aligning on header-based lookup (`X-Gateway-Api-Key`) since that's what a reverse-proxy client can set without modifying the path.
- The new login rate limiter initially blocked legitimate rapid requests during CI test runs (multiple signup/login calls in quick succession); loosened the threshold and scoped the limit by IP+email combination rather than IP alone, so parallel test users don't collide.
- First staging deploy failed silently on the health check — turned out `management.endpoints.web.exposure.include=health` hadn't propagated because of a stale environment variable cache on the platform; fixed by forcing a redeploy after confirming the env var.

## Known Limitations (carried forward)

- DNS rebinding still unaddressed — the target URL is validated once at registration time, not re-validated at the moment the gateway actually proxies a request.
- The fail-open/fail-closed policy itself is Person 1's decision; only the `active`-flag plumbing on this side exists so far, real enforcement behavior is still pending their implementation.
- The async logging path still uses fire-and-forget `@Async` — Week 2's test proves it clears 99.9% at the load levels tested, but it isn't structurally guaranteed at higher scale; an outbox-table pattern remains unimplemented.
