# Week 1 Journal — Project Setup & JWT Authentication
**Workstream:** Persistence, Auth & Backend Plumbing

## Objective
Stand up the Spring Boot project and the authentication core that the gateway and dashboard both depend on: JWT-based signup/login with hashed passwords and a stateless security configuration — no registration flow, no logging, no dashboard yet.

## Setup
- Generated project via Spring Initializr: Spring Boot 3.3.2, Java 17, Maven
- Dependencies added to `pom.xml`: `spring-boot-starter-web`, `spring-boot-starter-data-jpa`, `postgresql` (runtime scope), `spring-boot-starter-security`, `spring-boot-starter-validation`, `io.jsonwebtoken:jjwt-api`/`jjwt-impl`/`jjwt-jackson` (0.12.5), `spring-boot-starter-test`, `spring-security-test`
- `application.properties` reads `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET` and `JWT_EXPIRATION_MS` from environment variables, with local-development fallbacks only.

## Work Completed
1. **`User` entity and `users` table** — email (unique), BCrypt password hash, `createdAt`. No plaintext password field exists on the entity at all.
2. **JWT auth** — `JwtUtil` (HS256 via `io.jsonwebtoken`, signing key loaded from the `app.jwt.secret` property backed by the `JWT_SECRET` env var, default 24-hour expiry). The constructor rejects any secret under 32 bytes at startup with an `IllegalStateException`, since HS256 needs a key of at least 256 bits. `JwtAuthFilter` (`OncePerRequestFilter`) reads `Authorization: Bearer <token>`, calls `jwtUtil.extractEmail(...)` + `isTokenValid(...)`, and populates `SecurityContextHolder` when valid; an invalid or expired token simply leaves the request unauthenticated.
3. **`SecurityConfig`** — stateless session policy (`SessionCreationPolicy.STATELESS`), CSRF disabled (no session cookie to protect in a stateless JWT API), `/api/auth/**` and `/actuator/health` set to `permitAll()`, everything else requires authentication. `JwtAuthFilter` registered via `addFilterBefore(..., UsernamePasswordAuthenticationFilter.class)`. `BCryptPasswordEncoder` exposed as a bean here.
4. **Signup/login** — `AuthController` (`POST /api/auth/signup`, `POST /api/auth/login`) delegates to `AuthService`. Signup rejects a duplicate email, hashes the password and returns a token; login compares via `passwordEncoder.matches(...)` and returns the same generic "Invalid email or password" message whether the email or the password was wrong.

## Issues Faced and Resolved
- **A weak signing key would undermine every token.** HS256 is only as strong as its secret, and an environment variable can easily be set to something short. Resolved by making `JwtUtil` fail fast at startup if the configured secret is under 32 bytes, rather than silently running with a weak key.

## Known Limitations (by design, to be addressed Week 2)
- Only the `users` table is in use — no API registration, policies or request logs yet.
- Request bodies are not validated and errors are not yet returned in a consistent JSON shape.
- No automated tests yet.

# Week 2 Journal — Request Validation, Error Handling & Data Model
**Workstream:** Persistence, Auth & Backend Plumbing

## Objective
Harden the API surface and complete the data model: validated request bodies, consistent JSON error responses, and the remaining tables and repositories the registration flow and dashboard will sit on.

## Setup
- Local Postgres instance; schema applied manually from `schema.sql` rather than via `ddl-auto`. Deliberately set `spring.jpa.hibernate.ddl-auto=validate` instead of `update` so schema drift surfaces as a startup failure rather than a silent auto-migration.
- `spring.jpa.open-in-view=false` and `hibernate.jdbc.time_zone=UTC` set in `application.properties`.

## Work Completed
1. **Request validation** — `AuthDtos` records use `@NotBlank`, `@Email` and `@Size(min = 8)` on the password, enforced via `@Valid` on the controller.
2. **`GlobalExceptionHandler`** — `@RestControllerAdvice` mapping validation failures and `IllegalArgumentException` to 400, `BadCredentialsException` to 401 and `UsernameNotFoundException` to 404, each as a small JSON body instead of a stack trace.
3. **Entity/schema design** — added `registered_apis`, `policies` and `request_logs` alongside `users`, matching the proposal's data model, and mirrored them in a reference `schema.sql`. `Policy` is a separate entity from `RegisteredApi` (1:1 via `@OneToOne` + `@JoinColumn(unique = true)`) rather than inlined, so the algorithm (`TOKEN_BUCKET` / `SLIDING_WINDOW`), request budget, window and optional burst capacity can change without touching ownership data. `request_logs` carries an index on `(api_id, timestamp)` for dashboard queries.
4. **Repositories** — `UserRepository`, `RegisteredApiRepository` (including `findByGatewayApiKey`, the lookup the gateway will use to resolve a target and policy), `PolicyRepository` and `RequestLogRepository`.

## Issues Faced and Resolved
- **Raw exceptions would leak implementation detail to clients.** Without a handler, validation and credential errors surface as default Spring error payloads. Resolved with `GlobalExceptionHandler`, so every error from this API has the same simple JSON shape.
- **Schema drift should fail loudly.** Letting Hibernate auto-update tables could hide a mismatch between the entities and the real schema. Resolved by keeping `ddl-auto=validate` and maintaining `schema.sql` by hand.

## Known Limitations (by design, to be addressed Week 3)
- The new tables exist but nothing writes to them yet — no registration flow, no logging.
- Target URLs are not validated, so nothing stops an unsafe address being stored once registration is built.

# Week 3 Journal — API Registration & URL Validation
**Workstream:** Persistence, Auth & Backend Plumbing

## Objective
Build the API registration flow: an authenticated user registers a target API with a budget and algorithm choice, and the system refuses unsafe target URLs before anything is persisted.

## Setup
- No new dependencies. Uses the entities, repositories and error handling from Week 2.

## Work Completed
1. **API registration** — `ApiRegistrationController` (`POST /api/apis`, `GET /api/apis` for the caller's own APIs) and `ApiRegistrationService`. An authenticated user submits name + target URL + algorithm + budget; a `RegisteredApi` row and its paired `Policy` row are written inside one `@Transactional` block (so a failure on either side rolls both back), and a gateway API key (`UUID.randomUUID()`) is generated on the entity at construction time. Input is validated with `@NotBlank`, `@NotNull` and `@Min(1)` on the DTO.
2. **URL validation (proxy-abuse mitigation)** — `UrlValidationService.validateOrThrow(...)` parses the URL, confirms the scheme is `http`/`https`, resolves the host via `InetAddress.getByName(...)`, and rejects loopback, link-local, site-local (RFC1918), any-local, and multicast addresses, plus an explicit check for the `169.254.169.254` cloud metadata address. It runs before anything is saved.

## Issues Faced and Resolved
- **An open proxy is an SSRF risk.** Letting a user register any URL as a "target API" would let the gateway be pointed at `localhost`, private networks or the cloud metadata endpoint. Resolved by validating the resolved IP address, not just the URL text, before persisting.
- **`InetAddress.getByName()` does a live DNS resolution**, so the check depends on the network at registration time. A lookup failure currently surfaces as the same 400 as an unsafe URL — not yet distinguished (see Known Limitations).

## Known Limitations (by design, to be addressed Week 4)
- No rate-limit enforcement lives here — `registered_apis`/`policies` are pure storage; the gateway hasn't been pointed at them yet, so a registered API isn't actually protected end-to-end.
- DNS-failure vs. genuinely-invalid-host aren't distinguished in `UrlValidationService`.
- The target URL is validated once at registration, not re-checked when the gateway actually proxies a request.
- No request logging or dashboard endpoints yet.

# Week 4 Journal — Async Request Logging & Dashboard Endpoints
**Workstream:** Persistence, Auth & Backend Plumbing

## Objective
Make the system accountable: record every request outcome without slowing the request path, and expose aggregated, paginated data for the React dashboard.

## Setup
- No new dependencies. `@EnableAsync` added on `BackendApplication` so `@Async` methods actually run on a separate thread pool.

## Work Completed
1. **Async request logging** — `RequestLogService.logAsync(apiId, clientIdentity, outcome, latencyMs)`, marked `@Async`, writes a `RequestLog` row (outcome `ALLOWED`/`BLOCKED`, timestamp, client identity, optional latency) off the request path. It is the hook the gateway is meant to call after each request.
2. **Summary endpoint** — `GET /api/dashboard/{apiId}/summary` returns allowed vs. blocked counts for a time window (defaulting to the last 24 hours). Counts come from a `GROUP BY` query in `RequestLogRepository.countByOutcome(...)`, so aggregation happens in Postgres and raw logs are never sent to the browser.
3. **Paginated logs endpoint** — `GET /api/dashboard/{apiId}/logs` returns a `Page` of log entries, newest first, with `page` and `size` parameters, mapped to a `LogEntryResponse` DTO.
4. **Dashboard DTOs** — `SummaryResponse` and `LogEntryResponse` in `DashboardDtos`, so entities are never exposed directly.

## Issues Faced and Resolved
- **Logging must not add latency to the proxied request.** A synchronous database write on the request thread would count against the added-latency target. Resolved by making the write `@Async`.
- **Aggregating in Java would not scale.** Pulling rows into memory to count them would get slower as the log table grows. Resolved by pushing the counting into a `GROUP BY` query backed by the `(api_id, timestamp)` index.

## Known Limitations (by design, to be addressed Week 5)
- `@Async` is fire-and-forget: a crash between "response sent" and "row written" loses that log entry, and a failed write is not retried. This is the direct risk to the 99.9% completeness target.
- Nothing calls `logAsync` from a real proxied request yet, so no real traffic has been logged.
- The logs endpoint has no filtering beyond pagination, and the completeness metric is not yet instrumented.

# Week 5 Journal — Filtering, Log-Completeness Metric, Integration Tests & Project Completion
**Workstream:** Persistence, Auth & Backend Plumbing

## Objective
Finish the project: close the remaining dashboard gaps — filtering on the log view and instrumentation of the log-completeness metric named in the role brief (≥99.9% target) — back them with automated tests against a real database, and document the service for hand-off.

## Setup
- Added to `pom.xml`: `org.testcontainers:junit-jupiter` and `org.testcontainers:postgresql`, version `1.20.1` (held in a `testcontainers.version` property), both scoped to `test`.
- Tests need Docker running — they start a real, throwaway `postgres:16-alpine` container rather than substituting H2, so the actual JPQL queries are what's under test.

## Work Completed
1. **Filtering on the logs endpoint** — `GET /api/dashboard/{apiId}/logs` now accepts optional `outcome`, `clientIdentity` (partial match), `from` and `to` parameters, all independently combinable. Backed by a single JPQL query, `RequestLogRepository.findFiltered(...)`, using the `(:param IS NULL OR ...)` pattern per filter so a `null` means "no restriction" rather than needing a separate query method per combination.
2. **Log-completeness instrumentation** — `LogCompletenessService.measure(apiId, expectedCount, from, to)` compares an externally supplied "expected" request count against `RequestLogRepository.countByApiIdAndTimestampBetween(...)` for the same window and reports the ratio plus a `meetsTarget` boolean against the `0.999` constant. Exposed via `GET /api/dashboard/{apiId}/completeness?expected=...&from=...&to=...` using a `CompletenessResponse` DTO.
3. **`LogCompletenessIntegrationTest`** — fires 2,000 concurrent calls to `RequestLogService.logAsync(...)` from a 50-thread `ExecutorService`, waits for the `@Async` pool to flush (`CountDownLatch` plus a fixed settle delay), then asserts the completeness ratio is at least `0.999` against the real Postgres container.
4. **`RequestLogRepositoryFilterTest`** — four tests covering the outcome filter, the client-identity filter, the date-range filter, and confirming filtering never returns rows belonging to a different `apiId`.
5. **Developer documentation** — `README.md` lists every endpoint the dashboard calls, how to run the service locally, and how to run the tests, so the gateway and frontend workstreams can integrate against it.

## Issues Faced and Resolved
- **The completeness metric needs a trustworthy "expected" number.** The service cannot know how many requests were sent, so the count has to come from whoever drives the load. Resolved by making `expected` an explicit parameter and documenting the dependency, rather than guessing.
- **Test database setup differs from the real one.** `schema.sql` is not applied to a container that lives only for the test run, so the tests set `ddl-auto=create-drop` through `@DynamicPropertySource`; the application's own configuration stays on `validate`.

## Known Limitations (carried forward)
- The dashboard endpoints (`/summary`, `/logs`, `/completeness`) take `apiId` from the URL but do not check that the caller owns that API, so any authenticated user can read another user's data.
- `spring-boot-starter-actuator` is not in `pom.xml`, so `/actuator/health` (allowed in `SecurityConfig` and configured in `application.properties`) is not actually served yet.
- Unauthenticated requests rely on Spring Security's default behaviour; no custom entry point is configured, so the status returned for a missing token has not been explicitly set to 401.
- DNS-failure vs. genuinely-invalid-host are not distinguished, and target URLs are not re-validated at proxy time.
- No login throttling and no way to revoke a token before its 24-hour expiry.
- `RegisteredApi.targetUrl` has no explicit column type, while `schema.sql` defines it as `TEXT`; `User.email` is declared unique both at column and table level.
- Async logging remains fire-and-forget with no retry, and `LogCompletenessService` still depends on an externally supplied count. No CI pipeline yet.
