# Week 1 Journal — Multi-Tenant Auth & Schema Foundation
**Workstream:** Persistence, Auth & Backend Plumbing

## Objective
Stand up the multi-tenant backbone the gateway and dashboard both depend on: JWT-based signup/login, an API registration endpoint that stores a target URL + budget + algorithm choice, and the Postgres schema underneath it — no rate-limiting logic, no frontend, just accountable storage and auth.

## Setup
- Generated project via Spring Initializr: Spring Boot 3.3.2, Java 17, Maven
- Dependencies added to `pom.xml`: `spring-boot-starter-web`, `spring-boot-starter-data-jpa`, `postgresql` (runtime scope), `spring-boot-starter-security`, `spring-boot-starter-validation`, `io.jsonwebtoken:jjwt-api`/`jjwt-impl`/`jjwt-jackson` (0.12.5), `spring-boot-starter-test`
- Local Postgres instance; schema applied manually from `schema.sql` rather than via `ddl-auto`. Deliberately set `spring.jpa.hibernate.ddl-auto=validate` instead of `update` so schema drift surfaces as a startup failure rather than a silent auto-migration.

## Work Completed
1. **Entity/schema design** — four tables: `users`, `registered_apis`, `policies`, `request_logs`, matching the proposal's data model. `Policy` is a separate entity from `RegisteredApi` (1:1 via `@OneToOne` + `@JoinColumn(unique = true)`) rather than inlined, so the algorithm/budget can be swapped without touching ownership data.
2. **JWT auth** — `JwtUtil` (HS256 via `io.jsonwebtoken`, signing key loaded from the `app.jwt.secret` property backed by the `JWT_SECRET` env var). The constructor rejects any secret under 32 bytes at startup with an `IllegalStateException`, since HS256 needs a key of at least 256 bits. `JwtAuthFilter` (`OncePerRequestFilter`) reads `Authorization: Bearer <token>`, calls `jwtUtil.extractEmail(...)` + `isTokenValid(...)`, and populates `SecurityContextHolder` when valid.
3. **`SecurityConfig`** — stateless session policy (`SessionCreationPolicy.STATELESS`), CSRF disabled (no session cookie to protect in a stateless JWT API), `/api/auth/**` and `/actuator/health` set to `permitAll()`, everything else requires authentication. `JwtAuthFilter` registered via `addFilterBefore(..., UsernamePasswordAuthenticationFilter.class)`.
4. **Signup/login** — `AuthController` delegates to `AuthService`. Passwords hashed via `BCryptPasswordEncoder` (bean defined in `SecurityConfig`), never stored or logged in plaintext. Verified via `curl.exe`: `POST /api/auth/signup` returns a token, that token succeeds on a protected route (`Authorization: Bearer ...`), a missing or expired token returns 401.
5. **API registration** — `ApiRegistrationController`/`ApiRegistrationService`. An authenticated user submits name + target URL + algorithm + budget; a `RegisteredApi` row and its paired `Policy` row are written inside one `@Transactional` block (so a failure on either side rolls both back), and a gateway API key (`UUID.randomUUID()`) is generated on the entity at construction time.
6. **URL validation (proxy-abuse mitigation)** — `UrlValidationService.validateOrThrow(...)` parses the URL, confirms the scheme is `http`/`https`, resolves the host via `InetAddress.getByName(...)`, and rejects loopback, link-local, site-local (RFC1918), any-local, and multicast addresses, plus an explicit check for the `169.254.169.254` cloud metadata address. Verified: `http://localhost:8080` and `http://169.254.169.254/...` both rejected with 400; a real public URL accepted.

## Issues Faced and Resolved
- **`PasswordEncoder` bean collision.** Had briefly declared the `BCryptPasswordEncoder` bean in two `@Configuration` classes while restructuring the security setup, causing an ambiguous-bean error on startup. Fixed by consolidating the bean definition into `SecurityConfig` only.
- **`InetAddress.getByName()` does a live DNS resolution**, which meant the SSRF check could throw `UnknownHostException` on a genuinely offline network during testing, rather than cleanly rejecting the URL as invalid. Currently both cases (malformed host vs. DNS failure) surface as the same 400 — not yet distinguished (see Known Limitations).
- **Jackson couldn't serialize `Instant` fields by default** in earlier manual testing, producing a serialization error on any DTO containing a timestamp. Resolved by relying on Spring Boot's auto-registered `jackson-datatype-jsr310` module rather than writing a manual `Instant` converter.

## Known Limitations (by design, to be addressed Week 2)
- No rate-limit enforcement lives here yet — `registered_apis`/`policies` are pure storage; Person 1's gateway hasn't been pointed at them yet, so a registered API isn't actually protected end-to-end.
- Request logging (`RequestLogService.logAsync`) exists and is `@Async`, but nothing calls it yet since the proxy path isn't wired to this service — no real request has been logged.
- DNS-failure vs. genuinely-invalid-host aren't distinguished in `UrlValidationService` — both currently surface as the same 400.
- No integration tests yet against a real Postgres instance — currently manual `curl.exe` verification only.

# Week 2 Journal — Filtering, Log-Completeness Instrumentation & Real Integration Tests
**Workstream:** Persistence, Auth & Backend Plumbing

## Objective
Close two concrete gaps left open from Week 1: no filtering on the dashboard's log endpoint, and no actual instrumentation of the log-completeness metric named in the role brief (≥99.9% target). Back both with real automated tests against a real database instead of manual `curl.exe` verification.

## Setup
- Added to `pom.xml`: `org.testcontainers:junit-jupiter` and `org.testcontainers:postgresql`, version `1.20.1`, both scoped to `test`
- Requires Docker running locally (and eventually in CI) — tests now spin up a real, throwaway `postgres:16-alpine` container per test class rather than substituting H2, so the actual JPQL queries and schema are what's under test.

## Work Completed
1. **Filtering on the logs endpoint** — `GET /api/dashboard/{apiId}/logs` now accepts optional `outcome`, `clientIdentity`, `from`, and `to` query params, all independently combinable. Backed by a single JPQL query, `RequestLogRepository.findFiltered(...)`, using the `(:param IS NULL OR ...)` pattern per filter so a `null` means "no restriction" rather than requiring a separate query method per filter combination.
2. **Log-completeness instrumentation** — added `LogCompletenessService.measure(apiId, expectedCount, from, to)`, which compares an externally supplied "expected" request count against `RequestLogRepository.countByApiIdAndTimestampBetween(...)` for the same window, and reports the ratio plus a `meetsTarget` boolean against the `0.999` constant. Exposed via `GET /api/dashboard/{apiId}/completeness?expected=...&from=...&to=...`.
3. **`LogCompletenessIntegrationTest`** — fires 2,000 concurrent calls to `RequestLogService.logAsync(...)` from a 50-thread `ExecutorService`, waits for the `@Async` pool to flush (`CountDownLatch` + a fixed settle delay), then asserts the resulting completeness ratio clears `0.999` against the real Postgres container. Result: passed at this load level, confirming the fire-and-forget async write pattern doesn't meaningfully drop rows under 2,000 concurrent writes.
4. **`RequestLogRepositoryFilterTest`** — verifies the outcome filter, the client-identity partial-match filter, and the date-range filter independently against seeded rows, and confirms filtering never leaks rows belonging to a different `apiId`.
5. **Verified locally** — ran `mvn test` end-to-end with Docker Desktop running; both new test classes pass.

## Issues Faced and Resolved
- **Copy-paste import error** (`DynamicPropyRegistry` instead of `DynamicPropertyRegistry`) broke compilation on the first pass — caught immediately since it failed the build outright rather than silently misbehaving at runtime.
- **First test run was noticeably slower than expected** — Testcontainers pulls the `postgres:16-alpine` image from Docker Hub on first use. Subsequent runs are fast since the image layer is cached locally by the Docker engine.
- **Test database needed `ddl-auto=create-drop`, not the app's real `validate`** — `schema.sql` isn't applied automatically to a container that only exists for the test's lifetime. Scoped this override to `@DynamicPropertySource` in the test classes only; the real application config still fails loudly on schema drift.

## Known Limitations (carried forward / new this week)
- `LogCompletenessService` can't determine an "expected" count on its own — it depends on a number supplied externally (a load-test tally, or eventually Person 1's gateway keeping its own counter). Not yet wired to a real driver.
- DNS-failure vs. genuinely-invalid-host still aren't distinguished in `UrlValidationService` — not addressed this week, carried over from Week 1.
- No CI pipeline yet — `mvn test` has only been run locally so far, not gated on every push.

# Week 3 Journal — Security Review Pass: IDOR Fix, Schema-Drift Cleanup, Ownership Tests
**Workstream:** Persistence, Auth & Backend Plumbing

## Objective
No new features this week. Go back over everything built in Weeks 1–2 with a critical eye and fix what's found, treating this as the pass before handing the code off for real integration with the gateway and dashboard workstreams.

## Setup
No new dependencies. Same project, same Testcontainers-based test setup from Week 2.

## Work Completed
1. **Found and fixed an IDOR (Insecure Direct Object Reference) in `DashboardController`.** None of the three dashboard endpoints (`/summary`, `/logs`, `/completeness`) checked that the requesting user actually owned the `apiId` in the URL path — any authenticated user could view any other user's dashboard data just by changing the number. Fixed by adding `RegisteredApiRepository.existsByIdAndOwnerEmail(Long id, String ownerEmail)` and a `requireOwnership(apiId, authentication)` guard called at the top of every dashboard endpoint. On failure it throws `org.springframework.security.access.AccessDeniedException`, now mapped to a clean 403 JSON response via a new handler in `GlobalExceptionHandler`. Deliberately returns the same error message for "doesn't exist" and "exists but isn't yours" so the response itself can't be used to enumerate other users' API IDs.
2. **`RegisteredApiOwnershipTest`** — new test confirming `existsByIdAndOwnerEmail` returns true for the actual owner, false for a different registered user, and false for a nonexistent API ID, against the real Postgres container.
3. **Fixed schema/entity drift** — `RegisteredApi.targetUrl` had no explicit `@Column` type, so Hibernate's implicit default (`VARCHAR(255)`) silently diverged from `schema.sql`'s `TEXT` column definition. Added `columnDefinition = "TEXT"` so the entity and the real schema agree exactly, closing a gap that `ddl-auto=validate` wasn't reliably catching.
4. **Removed a redundant unique constraint** — `User.email` was declared unique twice: once via `@Column(unique = true)`, again via a table-level `@UniqueConstraint`. Consolidated to the single column-level declaration.
5. **Corrected a misleading code comment** in `UrlValidationService` — the comment on the `169.254.169.254` metadata-IP check implied it caught something the link-local range check (`isLinkLocalAddress()`) might miss. It doesn't; `169.254.169.254` already falls inside `169.254.0.0/16`. Comment rewritten to correctly describe this as a deliberate, explicit redundancy for a well-known address, not a genuine gap being closed.

## Issues Faced and Resolved
- **The IDOR was the significant find.** It had been sitting in working, "tested" code since Week 2 because manual `curl.exe` verification only ever exercised the happy path with a single account — never a second account probing another user's `apiId`.
- **Choosing the error response for the ownership check took deliberate thought.** Returning a distinct 403 vs. 404 for someone else's API would itself leak whether that `apiId` exists at all. Settled on one generic message and status code for both cases.

## Known Limitations (carried forward, unchanged this week)
- `LogCompletenessService` still depends on an externally supplied "expected" count — not yet wired to a real load driver or to Person 1's gateway.
- DNS-failure vs. genuinely-invalid-host still aren't distinguished in `UrlValidationService`.
- DNS rebinding is still unaddressed — the target URL is validated once at registration time, not re-validated at the moment the gateway actually proxies a request.
- No CI pipeline yet; `mvn test` has only been run locally.
- The async logging path is still fire-and-forget `@Async` — proven to clear 99.9% at the load levels tested in Week 2, not structurally guaranteed at higher scale. An outbox-table pattern remains unimplemented.
