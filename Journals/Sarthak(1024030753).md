# Week 1 — API Gateway Project

## Overview

Built and deployed iteration one of a self-service rate-limiting API gateway using **Spring Boot / Spring Cloud Gateway**, **Redis-backed token bucket via Bucket4j**, **PostgreSQL persistence**, and **JWT authentication**, along with a **React analytics dashboard**. The system is deployed locally using **Docker Compose**.

Below are the three technical issues from this week that were non-obvious enough to be worth recording.

---

## Issue 1: Spring Boot / Spring Cloud Version Incompatibility

### Error

```text
CompatibilityNotMetException: Spring Boot [3.4.7] is not compatible with
this Spring Cloud release train. Change Spring Boot version to one of the
following versions [3.5.x].
```

### Relevant Context

`pom.xml` pinned the parent to:

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.4.7</version>
</parent>

<properties>
    <spring-cloud.version>2025.0.0</spring-cloud.version>
</properties>
```

The application failed at startup, before any of my own code ran, while constructing a bean called:

```text
compositeCompatibilityVerifier
```

### Key Observation

Spring Cloud release trains ship their own runtime compatibility check that runs during application context startup and refuses to boot outside their declared supported Spring Boot version range.

This wasn't a build-time Maven dependency conflict — the project compiled successfully. Instead, it was a deliberate **runtime compatibility guard**.

### Solution

Bumped the Spring Boot parent version to **3.5.3**, which was the newest version actually available in Maven Central at the time.

This was confirmed by querying Maven Central's own index rather than relying solely on Spring Initializr's default suggestion, which pointed toward an unreleased version that wasn't yet resolvable.

### Because

Spring Cloud versions its own release trains independently of Spring Boot, and each release train targets a specific range of Spring Boot versions.

Picking Spring Boot and Spring Cloud versions independently, without checking the compatibility matrix first, caused the issue.

The fix isn't simply:

> "Use a newer version."

It's:

> **"Cross-reference the Spring Boot and Spring Cloud compatibility matrix before pinning either version."**

---

## Issue 2: Reverse-Proxy Path-Stripping Never Reaching the Origin

### Error

There was no exception — this was a **silent correctness bug**.

Requests through the gateway succeeded, but the origin server was receiving the full:

```text
/proxy/{apiKey}/...
```

path instead of the path the caller intended.

### Relevant Context

The gateway's rate-limiting filter mutates the request path to strip the `/proxy/{apiKey}` prefix before forwarding:

```java
GatewayFilter filter = (exchange, chain) -> {
    // ...
};

return filter;
```

The filter was registered without an explicit order.

The automated test suite passed because its embedded origin server matched any path:

```text
/**
```

Therefore, it never checked which exact path actually arrived.

The bug only surfaced when running the gateway live against a real **nginx origin server inside Docker**.

### Key Observation

Spring Cloud Gateway's internal `RouteToRequestUrlFilter`, with order `10000`, resolves and caches the backend target URL from the request **before** an unordered filter gets a chance to run.

An unordered gateway filter defaults to:

```text
LOWEST_PRECEDENCE
```

Therefore, the path mutation was logically correct but happened **too late** for the routing machinery to use it.

### Solution

Wrapped the filter in an `OrderedGatewayFilter` with:

```java
Ordered.HIGHEST_PRECEDENCE
```

This forces the filter to execute before route resolution.

I also strengthened the integration test so that the origin server captures and asserts the **exact path** it receives.

This prevents the same class of bug from being hidden behind an overly permissive test double.

### Because

In a filter-chain framework, correctness depends not only on **what** a filter does, but also on **when** it runs.

An unordered filter isn't really "no order" — it effectively runs very late.

The path mutation itself was correct. The problem was that it happened after the routing machinery had already determined the target request.

> **Correct logic + incorrect execution order = incorrect system behavior.**

## Issue 3: API Key Exposed via URL Path

### Error

There was no runtime error.

This was a **security design flaw** discovered through inspection rather than a failing test.

The gateway originally used:

```text
/proxy/{apiKey}/**
```

which meant every request embedded the API key directly into the URL.

### Relevant Context

Example request:

```bash
curl http://gateway/proxy/agw_XXXX/get
```

### Key Observation

URLs — unlike headers — routinely end up in places outside the request's own transport security, including:

* Web server access logs
* Browser history
* Proxy logs
* Monitoring systems
* Analytics systems
* The `Referer` header in certain browser scenarios

TLS protects the URL path in transit just as it protects headers, so this was **not primarily an interception problem**.

The problem was that URLs are much more likely to be persisted or exposed after the request completes successfully.

### Solution

Moved the API key from the URL path into an HTTP header:

```http
X-Api-Key: agw_XXXX
```

The gateway now uses a common route:

```text
/proxy/**
```

and determines the API registration from the API key provided in the header.

The old behavior was also verified manually:

```bash
curl http://gateway/proxy/agw_XXXX/get
```

now correctly returns:

```text
404
```

while:

```bash
curl -H "X-Api-Key: agw_XXXX" http://gateway/proxy/get
```

works correctly.

This confirmed that the old URL-based API key path was genuinely removed rather than simply hidden.

### Because

Secrets should be transmitted through mechanisms that minimize accidental persistence and exposure outside the request itself.

Headers are generally preferable to URLs for API credentials because URLs are frequently logged, cached, stored in browser history, or propagated through other systems.

This follows the same general principle used by major API providers such as **Stripe, GitHub, and AWS**:

> **Don't put secrets in URLs when they can be sent through headers instead.**

---

## Week 1 Takeaways

The three issues highlighted three different types of engineering problems:

| Issue                               | Type                       | Main Lesson                                                     |
| ----------------------------------- | -------------------------- | --------------------------------------------------------------- |
| Spring Boot / Cloud incompatibility | Dependency / Configuration | Check compatibility matrices before choosing framework versions |
| Path stripping order                | Runtime / Architecture     | Filter ordering matters as much as filter logic                 |
| API key in URL                      | Security / Design          | Keep secrets out of URLs and use headers instead                |

The biggest takeaway from this iteration was that building a working backend isn't only about making the happy path function. **Framework lifecycle, execution order, integration-test quality, and security boundaries can all create bugs that aren't visible from the application code alone.**


# Week 2 — API Gateway Project

## Overview

Built the React analytics dashboard on top of iteration one: a new analytics API providing **allowed/blocked request totals, hourly traffic buckets, and paginated request logs**, along with the corresponding frontend for authentication, API registration/list/detail pages, a Recharts traffic chart, and a request log table.

Below are the three technical issues from this week that were non-obvious enough to be worth recording — two real bugs found and fixed, and one gap found and documented for a later fix.

---

## Issue 1: Duplicate Hour Buckets on the Traffic Chart

### Error

No exception was thrown — this was a **silent rendering bug**.

The dashboard displayed a tall bar on the traffic chart, but hovering over it showed a tooltip containing:

```text
Allowed: 0
Blocked: 0
```

### Relevant Context

The backend bucketed the last 24 hours of request logs into one-hour windows:

```java
Instant since = Instant.now().minus(24, ChronoUnit.HOURS);
Instant cursor = since.truncatedTo(ChronoUnit.HOURS);
Instant now = Instant.now();

while (!cursor.isAfter(now)) {
    // ...
    points.add(
        new TrafficPoint(
            HOUR_LABEL.format(cursor),
            counts[0],
            counts[1]
        )
    );

    cursor = cursor.plus(1, ChronoUnit.HOURS);
}
```

Each bucket's label was formatted as:

```text
HH:mm
```

with no date component.

### Key Observation

`since.truncatedTo(HOURS)` rounds down to the beginning of the hour rather than representing exactly 24 hours before `now`.

Combined with looping until the current, non-truncated `now`, the window could span **25 hourly steps instead of 24**.

This meant the generated labels could contain the same hour-of-day twice. For example:

```text
03:00  ← previous day
...
03:00  ← current day
```

Because the label contained only `HH:mm`, Recharts treated both buckets as the same category.

The chart therefore rendered a bar for the real data, but the hover target could resolve to the empty duplicate bucket, producing:

```text
Allowed: 0
Blocked: 0
```

### Solution

Anchored the loop at the current hour and walked backwards exactly 23 hours:

```java
Instant end = now.truncatedTo(ChronoUnit.HOURS);
Instant cursor = end.minus(23, ChronoUnit.HOURS);
```

This guarantees exactly **24 consecutive hourly buckets**, which by construction cannot repeat an hour-of-day.

Added `AnalyticsServiceTest` to assert exactly 24 distinct labels across seven different times of day.

The old implementation would fail intermittently depending on the time at which the test happened to run, which is why a single fixed-time test would not have reliably caught the issue.

### Because

A time-window loop's correctness depends on **where the window is anchored**.

The original implementation anchored the loop at an already-rounded intermediate value:

```text
now
 ↓
minus 24 hours
 ↓
truncate to hour
 ↓
loop until untruncated now
```

That allowed the effective window to drift by one hour under specific timing conditions.

The corrected implementation instead anchors at a fixed hourly boundary and generates an exact number of buckets:

```text
truncated now
 ↓
minus 23 hours
 ↓
24 consecutive hourly buckets
```

> **Time windows should be anchored at a fixed boundary and generated for an explicit number of periods rather than relying on a rounded start and moving end point.**

## Issue 2: CORS Allowed-Headers Gap for X-Api-Key

### Error

While writing a browser-based verification script for the gateway's `/proxy/**` path, the request failed during the CORS preflight stage:

```text
Access to fetch at 'http://localhost:8080/proxy/get'
from origin 'http://localhost:5173'
has been blocked by CORS policy:
Response to preflight request doesn't pass access
control check: No 'Access-Control-Allow-Origin' header is present
on the requested resource.
```

### Relevant Context

The backend's CORS configuration explicitly allowlisted:

```java
configuration.setAllowedHeaders(
    List.of("Authorization", "Content-Type")
);
```

However, the gateway uses:

```text
X-Api-Key
```

as the header that identifies which registered API a proxied request belongs to.

The optional per-caller header:

```text
X-Client-Id
```

was also not included in the allowlist.

### Key Observation

This gap was invisible during earlier testing because all `/proxy/**` requests had been tested through `curl`.

`curl` is not subject to browser CORS enforcement.

A browser-based request follows a different flow:

```text
Browser
   ↓
CORS preflight
   ↓
Access-Control-Allow-Headers
   ↓
Actual request
```

Therefore, a successful `curl` request proved that the gateway endpoint worked for a command-line HTTP client, but said nothing about whether a browser-based API consumer could successfully call the same endpoint.

The gateway's actual API key header was precisely the header that the browser's preflight needed permission to send.

### Solution

**Fix deferred — documented for a later change.**

The planned change is to add both gateway-specific headers to the CORS configuration:

```java
configuration.setAllowedHeaders(
    List.of(
        "Authorization",
        "Content-Type",
        "X-Api-Key",
        "X-Client-Id"
    )
);
```

The fix was deferred because the dashboard itself does not directly call `/proxy/**`. That endpoint is intended for external API consumers, so the issue does not block the current dashboard work.

It is nevertheless a real compatibility gap for anyone building a browser-based client against the gateway.

### Because

A test suite's coverage is bounded by the **transport it uses to exercise the system**, not just by the code paths it reaches.

`curl` and browser `fetch()` are not equivalent callers when browser-specific mechanisms such as CORS are involved.

Testing:

```text
curl → gateway
```

does not test:

```text
browser → preflight → CORS validation → gateway
```

> **A passing test suite only proves what its transport can actually exercise.**

## Issue 3: Dev-Server Proxy Prefix Collision Blanked the Page on Reload

### Error

No application exception was surfaced in the console beyond a `401`.

Reloading the API detail page:

```text
/apis/{id}
```

produced a completely blank white page.

The document contained an empty title and no application body content.

### Relevant Context

The Vite development server proxied backend requests using:

```javascript
proxy: {
    '/auth': 'http://localhost:8080',
    '/api': 'http://localhost:8080',
    '/proxy': 'http://localhost:8080',
},
```

The frontend's own client-side route for the API detail page was:

```text
/apis/{id}
```

### Key Observation

Vite matches proxy configuration keys as **path prefixes**, not exact path segments.

Therefore:

```text
/api
```

also matched:

```text
/apis/{id}
```

because `/apis` starts with the literal string `/api`.

During a full-page reload, Vite therefore proxied:

```text
/apis/{id}
```

to the backend instead of serving the React application's `index.html`.

The backend has no route for:

```text
/apis/{id}
```

Its API routes are instead under:

```text
/api/apis/{id}
/api/apis/{id}/stats
```

Spring Security's:

```text
.anyExchange().authenticated()
```

rule consequently rejected the unauthenticated document request with:

```text
401 Unauthorized
```

The browser received a `401` response instead of the SPA's HTML document, resulting in the blank page.

### Solution

Changed the Vite proxy match key from:

```javascript
'/api': 'http://localhost:8080',
```

to:

```javascript
'/api/': 'http://localhost:8080',
```

Every genuine backend call still matches:

```text
/api/apis
/api/apis/{id}
/api/apis/{id}/stats
```

while the frontend route:

```text
/apis/{id}
```

does not, because the character after `/api` is `s` rather than `/`.

Verified by reloading the API detail page and confirming that:

* The page title renders correctly.
* The application body renders correctly.
* The traffic chart renders correctly.
* The actual traffic bar is displayed with the correct data.

### Because

A prefix-based proxy configuration is only effectively exact when the chosen prefix cannot collide with another route.

To a human reader:

```text
/api
/apis
```

look like separate namespaces.

To a prefix matcher, however:

```text
/apis
^^^^
/api
```

is a valid match.

The fix was therefore not to add another route, but to make the existing proxy match **unambiguous**.

> **Prefix-based routing needs to be checked against every route sharing the same namespace, not just the routes the proxy was originally intended to handle.**

# Week 3 — API Gateway Project

## Overview

Hardened authentication behavior and cleaned up local environment/tooling discipline after live-testing the dashboard end to end. Two of this week's three issues were the **same visible symptom caused by two genuinely separate code paths**, which reinforced the need to verify a fix against every path that can produce the observed behavior.

Below are the three technical issues from this week that were non-obvious enough to be worth recording.

---

## Issue 1: Unauthenticated Requests Triggered the Browser's Native Login Popup

### Error

No application exception appeared in the logs.

Visiting the dashboard without a valid session produced the browser's native **"Sign in"** credential dialog with username/password fields instead of the application's intended authentication behavior.

A direct request to the backend showed:

```bash
curl -i http://localhost:8080/api/apis
```

returning:

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Realm"
```

### Relevant Context

HTTP Basic authentication was explicitly disabled in the Spring Security configuration:

```java
.httpBasic(ServerHttpSecurity.HttpBasicSpec::disable)
```

The application was intended to use JWT-based authentication instead.

### Key Observation

Browsers treat a `401 Unauthorized` response containing:

```text
WWW-Authenticate: Basic
```

as an instruction to display their own native HTTP Basic credential prompt.

The important distinction was that disabling HTTP Basic authentication:

```java
.httpBasic(...)
```

stops Spring Security from **accepting Basic credentials**, but it does not necessarily remove Basic authentication from every authentication failure response.

Spring Security's default exception-handling behavior could still use a Basic authentication entry point when generating a `401`.

Therefore, the browser interpreted the response as:

```text
401
+
WWW-Authenticate: Basic
        ↓
Native browser login popup
```

### Solution

Configured an explicit authentication entry point that returns a bare `401` response:

```java
.exceptionHandling(exceptionHandling ->
    exceptionHandling.authenticationEntryPoint(
        (exchange, ex) -> {
            exchange.getResponse()
                .setStatusCode(HttpStatus.UNAUTHORIZED);

            return Mono.empty();
        }
    )
)
```

This prevents the response from containing the unwanted:

```text
WWW-Authenticate: Basic
```

header.

Verified directly against the running backend that the header was absent and added a test asserting that `WWW-Authenticate` is not present for an unauthenticated request.

### Because

Disabling a mechanism and removing its side effects are not necessarily the same operation.

In this case:

```text
Disable HTTP Basic
        ↓
Spring Security no longer authenticates using Basic
```

did not automatically mean:

```text
No Basic-related response headers
```

The default authentication entry point was still capable of producing the Basic challenge header.

> **When changing authentication behavior, disabling a mechanism is not enough — its failure-handling and fallback behavior also needs to be checked.**

## Issue 2: The Same Symptom From a Genuinely Different Code Path

### Error

The exact same native browser login popup appeared **after Issue 1 had already been fixed and verified**.

This time, however, the request contained a real but invalid/expired JWT.

### Relevant Context

Testing with an invalid bearer token:

```bash
curl -i http://localhost:8080/api/apis \
  -H "Authorization: Bearer not-a-real-token"
```

returned:

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Realm"
```

The custom JWT filter was configured as:

```java
AuthenticationWebFilter jwtFilter =
    new AuthenticationWebFilter(authenticationManager);

jwtFilter.setServerAuthenticationConverter(authenticationConverter);

// no setAuthenticationFailureHandler(...) call
```

### Key Observation

The JWT `AuthenticationWebFilter` had its **own default authentication failure handler**.

Inspecting the implementation showed that its default failure handler was effectively:

```java
new ServerAuthenticationEntryPointFailureHandler(
    new HttpBasicServerAuthenticationEntryPoint()
)
```

This was a separate mechanism from the authentication entry point configured in Issue 1.

There were therefore two different authentication failure paths:

```text
No token
   ↓
Spring Security exception handling
   ↓
Authentication Entry Point
   ↓
401
```

and:

```text
Invalid JWT
   ↓
AuthenticationWebFilter
   ↓
Authentication Failure Handler
   ↓
401
```

Both paths could produce:

```text
401
WWW-Authenticate: Basic
```

and therefore both could trigger the browser's native login popup.

Fixing the first path did not automatically change the second.

### Solution

Configured an explicit failure handler directly on the JWT authentication filter:

```java
jwtFilter.setAuthenticationFailureHandler(
    (webFilterExchange, exception) -> {
        webFilterExchange
            .getExchange()
            .getResponse()
            .setStatusCode(HttpStatus.UNAUTHORIZED);

        return Mono.empty();
    }
);
```

Added a second authentication test using a syntactically invalid bearer token alongside the existing no-token test.

This ensured that both authentication failure paths were explicitly covered.

### Because

The visible symptom was identical:

```text
Browser → Native Login Popup
```

but the internal execution paths were different.

The first issue exercised:

```text
No authentication
```

while this issue exercised:

```text
Authentication attempted → JWT validation failed
```

They were handled by different components with different default behavior.

Therefore, fixing one reproduction only proved that **one execution path** had been fixed.

> **When the same symptom can originate from multiple code paths, each path needs its own reproduction and test.**

This was particularly important here because JWTs are time-limited. A real returning user with an expired token is more likely to exercise the invalid-token path than the completely unauthenticated path.

## Issue 3: Concurrent Dev-Server Instances Caused Repeated, Confusing CORS Failures

### Error

Intermittent `403` / CORS failures appeared during login testing.

The failures occurred repeatedly across the testing session even though the backend's CORS configuration had not changed.

The same login flow could work in one run and fail in another.

### Relevant Context

The backend's CORS allowlist was configured with:

```yaml
allowed-origins: ${CORS_ALLOWED_ORIGINS:http://localhost:5173,http://localhost:4173}
```

Multiple `npm run dev` instances had ended up running simultaneously.

Some were started for verification/testing purposes, while another was running independently for normal manual development.

### Key Observation

Vite's development server automatically moves to the next available port when its default port is already occupied.

For example:

```text
5173
 ↓
5174
 ↓
5175
```

The backend, however, only allowed:

```text
http://localhost:5173
http://localhost:4173
```

Therefore, if the frontend was silently moved to `5174`, its requests were coming from an origin that was **not present in the CORS allowlist**.

The behavior depended on which process happened to acquire the port first:

```text
Single dev server
       ↓
localhost:5173
       ↓
CORS allowed
       ↓
Works
```

versus:

```text
Multiple dev servers
       ↓
5173 already occupied
       ↓
Vite starts on 5174
       ↓
Origin not allowlisted
       ↓
CORS failure
```

This made the issue appear intermittent and difficult to reproduce.

### Solution

Killed all stale and duplicate development-server processes.

Established a development rule going forward:

> **Exactly one dev-server instance should run at a time, owned by whoever is actively using it.**

Verification tooling and manual testing should not independently start additional Vite instances against the same local port range.

### Because

A CORS allowlist is a contract with a specific origin.

The backend was correctly configured to allow:

```text
localhost:5173
```

but the development environment was sometimes silently producing:

```text
localhost:5174
```

The resulting failure was therefore not an application-code bug. It was an **environment and process-management problem**.

The key issue was treating the development server as if it had a fixed identity while allowing multiple processes to compete for its port.

> **Shared local resources such as ports need explicit ownership rules, otherwise environment-dependent failures become non-deterministic and difficult to reproduce.**
