Week 1 — API Gateway Project
Overview
Built and deployed iteration one of a self-service rate-limiting API gateway (Spring Boot / Spring Cloud Gateway backend, Redis-backed token bucket via Bucket4j, PostgreSQL persistence, JWT auth) plus a React analytics dashboard, with a working local deployment via Docker Compose. Below are the three technical issues from this week that were non-obvious enough to be worth recording.

Issue 1: Spring Boot / Spring Cloud Version Incompatibility
Error:


CompatibilityNotMetException: Spring Boot [3.4.7] is not compatible with
this Spring Cloud release train. Change Spring Boot version to one of
the following versions [3.5.x].
Relevant Context

pom.xml pinned the parent to:


<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.4.7</version>
</parent>
<properties>
  <spring-cloud.version>2025.0.0</spring-cloud.version>
</properties>
The application failed at startup, before any of my own code ran, while constructing a bean called compositeCompatibilityVerifier.

Key Observation

Spring Cloud release trains ship their own runtime compatibility check that runs during context startup and refuses to boot outside their declared supported Boot version range — this isn't a build-time Maven dependency conflict (the project compiled fine), it's a deliberate runtime guard.

Solution

Bumped the parent to 3.5.3 — the newest version that Maven Central actually had available at the time (confirmed by querying Central's own index rather than trusting Spring Initializr's default suggestion, which pointed at an unreleased 4.1 line not yet resolvable at all).

Because

Spring Cloud versions its own train (2025.0.0 here) independently of Spring Boot, and each train targets a narrow Boot version range. Picking Boot and Spring Cloud versions independently, without checking the compatibility matrix first, is what caused this — the fix isn't just "use a newer version," it's "cross-reference the two version schemes before pinning either one."

Issue 2: Reverse-Proxy Path-Stripping Never Reaching the Origin
Error

No exception — a silent correctness bug. Requests through the gateway succeeded, but the origin server was receiving the full /proxy/{apiKey}/... path instead of the path the caller intended.

Relevant Context

The gateway's rate-limiting filter mutates the request path to strip the /proxy/{apiKey} prefix before forwarding:


GatewayFilter filter = (exchange, chain) -> { ... };
return filter; // registered with no explicit order
The automated test suite passed, because its embedded origin server matched any path ("/**"), so it never noticed which path actually arrived. The bug only surfaced running the gateway live against a real origin (nginx) in Docker.

Key Observation

Spring Cloud Gateway's internal RouteToRequestUrlFilter (order 10000) resolves and caches the backend target URL from the request before an unordered filter — which defaults to LOWEST_PRECEDENCE — gets a chance to run. So the path mutation was computed correctly, just too late for the routing machinery to see it.

Solution

Wrapped the filter in OrderedGatewayFilter with Ordered.HIGHEST_PRECEDENCE, forcing it to run before route resolution. Also strengthened the test's origin server to capture and assert the exact path it received, so this class of bug can't hide behind a permissive test double again.

Because

In a filter chain framework, correctness of what a filter does is separate from when it runs — an unordered filter isn't "no order," it's "last," and forgetting that is what let a logically-correct path mutation get discarded before anything downstream could use it.

Issue 3: API Key Exposed via URL Path
Error

No runtime error — a security design flaw caught by inspection, not a test failure. The gateway path was /proxy/{apiKey}/**, meaning every call embedded the secret key directly in the URL.

Relevant Context


curl http://gateway/proxy/agw_XXXX/get
Key Observation

URLs — unlike headers — routinely end up in places outside the request's own transport security: web server access logs, browser history, and the Referer header a browser sends to a third-party origin on any follow-up request from the same page. TLS protects the path in transit exactly as well as it protects headers, so this was never an interception risk — it was a risk of the key leaking into logs and history after the request completed successfully.

Solution

Moved the key into an X-Api-Key header. Every registered API now shares one path, /proxy/**; the routing layer's predicate matches on the header value instead of a path segment. Verified by hand afterward: calling with the header works, calling with the key still embedded in the URL (old behavior) now correctly 404s, confirming the old path is genuinely gone rather than just hidden.

Because

Secrets belong in channels that aren't persisted or logged by default outside the transport itself — headers qualify, URLs don't. This is the same reason real API providers (Stripe, GitHub, AWS) never accept API keys as URL parameters.****
